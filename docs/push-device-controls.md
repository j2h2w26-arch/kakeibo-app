# 端末別Push設定・受信処理（⑥-2）

更新: 2026-10-06。⑥-1のDraft PR #25に積み上げる変更。本番未反映、実配信なし。送信機能・テスト通知ボタン・定期配信は次段階。

## 今回の変更

- 設定に「アプリを閉じていても届く通知」を追加。準備中/非対応/拒否/オフ/登録済み/要確認を区別。端末名と明示同意を必須にする。
- `VITE_PUSH_ENABLED=true`かつ有効な形式の`VITE_PUSH_PUBLIC_KEY`がなければ準備中。標準は無効で、通知許可要求も新規購読も行わない。現時点で有効化しない。
- 許可要求は本人が登録ボタンを押したイベント内のみ。時刻設定の保存はOS許可を要求せず、アプリ内お知らせだけでも保存可能にする。
- 通知先の登録/本人端末一覧/解除は⑥-1の3RPCだけ。操作開始時のJWTをリクエストに固定し、通信途中でアカウントが変わっても別人のトークンで登録しない。8秒でHTTP待機を打ち切り、サーバーの詳細エラーや配送先は画面・ログへ出さない。
- IndexedDBには所有者ID、購読レコードID、ローカル同意、有効状態、世代番号だけを保存。endpoint・購読鍵・JWT・家計データは追加保存しない。SWと同じDB契約をテストで確認。
- Web Locksでタブ間の購読操作を直列化。アカウント境界/停止ではロックを待つ前に同意を無効化し、登録途中の応答を拒否。BroadcastChannelで別タブの表示と二重通知抑制状態を再確認する。
- 停止は端末側の同意無効化、ブラウザーunsubscribe、サーバー削除。部分失敗を完了表示せず、再試行を案内。ストレージ書込み失敗時もunsubscribeを試みる。ログアウトは停止確認を最大2.5秒待ち、確認不能を案内したうえで継続する。
- セッション復元/画面復帰時に所有者・OS許可・サーバー登録を照合。検証不能なら安全側へ端末停止を試みる。**オフラインでアプリを開いた場合なども、再接続後の再確認・明示再登録が必要になることがある。**
- Push登録中/確認不能時は従来の朝夕OS通知を抑止し、画面内のまとめは残す。ログアウト後に遅延した従来OS通知もeffectの終了で抑止する。

## 受信と更新

WorkboxのgenerateSWを維持し、`importScripts: ['/push-worker.js']`で受信処理のみを追加。同じ`/sw.js`と`/`scopeを使い、install/activate/skipWaitingを追加しない。既存の明示更新・別タブ保護・アプリシェルのキャッシュを維持する。

将来の送信側とのpayload契約:

```json
{
  "type": "futari-daily-v1",
  "subscriptionId": "登録RPCが返したUUID",
  "scheduledAt": 1791193200000,
  "expiresAt": 1791196800000
}
```

時刻はUnixミリ秒。予定が未来、期限切れ、予定〜期限が1時間超、型不正、他の購読ID、同意無効、所有者不一致、OS拒否は表示しない。通知本文は固定一般文、遷移先は同一originの`/`固定。payload内のtitle/body/urlは利用しない。購読更新イベントで勝手に新しい通知先を登録しない。

同じtagは表示の重複を軽減するだけで、永続的な重複排除や配送保証ではない。送信台帳・再試行・期限・失効処理は次段階で必須。取り消し直前の受付済み通知や、ブラウザー独自の通知表示まで完全に取り消す保証はしない。

- 登録失敗の巻戻し、拒否後の再要求なし、時刻設定だけで購読しない、解除の部分失敗、遅延した登録応答、ログアウト/アカウント切替、トークン更新、ストレージ障害を確認。
- 受信workerを隔離VMで実行。一般文、同一origin固定、同意/所有者/期限/不正payload/ストレージ障害の拒否を確認。
- `dev/push-settings.html`は合成画面。390px/1280px表示、同意前ボタン無効、登録/停止の表示、拒否/オフライン案内を確認。実IndexedDBの専用QAストアで5同時更新を保持。開発用画面はproduction buildに含めない。

- `npm run lint`成功、`npm run build`成功。PreviewはPRに記録。従来の500kB超チャンク警告は残る。

未確認: 実Auth/Data APIのJWT経路、実購読URLの対応範囲、iPhone/Android/SurfaceでのOS許可・背景受信・タップ・解除・端末間競合、Push追加後の実端末旧版→新版更新。DB移行は未適用のためPreviewで登録成功を試さない。匿名/第三者拒否は前段の隔離SQL試験を維持しているが、実HTTPの合格証明ではない。

## 次段階と本番ゲート

1. 認証付きテスト送信、VAPID、配信対象抽出、台帳の原子的確保/期限/再試行/重複排除を実装。通知payloadに個人情報を追加しない。
2. 許可された隔離Supabaseで実RPCとOS動作を確認。本人がテスト通知ボタンを押した端末だけを対象とする。
3. Draft PR/Preview承認後、無効状態でDB・送信関数を適用し検証。公開鍵だけをクライアントへ設定。秘密鍵はサーバーSecrets/Vaultのみ。
4. 本人の端末登録と実機確認後に定期配信を明示承認して開始する。フロントのフラグだけをオフにしても閉じた既存端末への配信を即時停止できないので、停止は送信側でも必須。
