# バックグラウンドPush通知 — 承認済み方針（段階⑥）

更新: 2026-10-05。利用者の「よい！！」で推薦方針の実装を承認済み。**本番DB適用・鍵設定・購読登録・配信・Cron変更はPR/Preview確認後の別承認。** 登録/解除の最初の実装は[進捗と検証](push-subscription-foundation.md)を参照。下記の受入テスト全体が完了したわけではない。

## 現状と目的

`useDailyReminder.js`はアプリが開かれた状態のeffectで時刻/件数を評価し、画面内表示と許可済みOS通知を出す。localStorageで利用者・日付・朝夕を区別する。`DailyReminderSettings.jsx`と`notification_preferences`に朝夕の時刻があるが、Push購読・サーバー配信台帳・受信ハンドラーはない。SWは現在generateSWで生成される。閉じたアプリに時刻通知できるという意味ではない。

目的は、許可した端末に限り、アプリを開いていなくても「今日やることを確認する」きっかけを届けること。目覚ましや必達通知として扱わない。

2026-10-02の本番読取り確認ではpg_cron/pg_net/supabase_vaultが導入済み、Cronはポイ活の2ジョブのみ。通知関連の公開テーブルはnotification_preferencesのみだった。既存基盤があることはPush機能の実装済みを意味しない。

## 利用者が承認した推薦方針

- 全端末で初期状態オフ。「この端末で通知を受け取る」を本人が押し、OSで許可して初めて登録。既存の通知設定から勝手にPushをオンにしない。
- 朝08:00・夕19:00（日本時間）を初期表示し、個人別に変更/片方だけも可能。既存時刻は確認画面に引き継ぐが自動同意とはしない。
- **自分が許可した各端末**へ送る。夫の許可で妻の端末を登録しない。端末ごとに停止/削除できる。
- 未購入品、期限間近在庫、本人の未完了ポイ活、予定のあるWish、今日期限/期限超過の家事のいずれかがある場合だけ通知。初版は既存todaySummaryと同じ対象。人生ToDo/人生設計の新しい通知は追加しない。
- ロック画面には「ふたりの暮らし：今日のやることを確認しましょう」の一般文だけ。金額、品名、相手の名前、画像は送らない。タップで同一サイトのホームを開き、ログイン後に詳細を確認する。
- 通知予定時刻から最大1時間までを有効期間とし、古い朝の通知を夜に再送しない。遅延/不達はあり得る。初回テスト通知も本人のボタン操作だけ。
- 新規有料通知サービスを契約せず、既存Supabase Freeと標準Web Pushを使う案。無料枠超過や新たな課金が必要なら停止して相談する。

UA名だけで判断せず、Notification・serviceWorker・PushManager等を機能検出する。非対応なら理由とホーム画面追加/設定案内を表示し、画面内のお知らせを残す。拒否後に自動で許可ダイアログを繰り返さない。省電力、集中モード、機内モード、ブラウザー強制停止、端末電源オフでは遅延/不達がある。API受付成功を端末への到着確認と呼ばない。

## 配信基盤・費用の案

`Supabase Cron → 内部認証付きEdge Function → ブラウザー提供元のPushサービス → SW → OS通知`。

- [Supabase公式](https://supabase.com/docs/guides/functions/schedule-functions)のpg_cron/pg_netとVaultを利用候補とする。ポイ活向けの既存ジョブ/秘密情報は変更・流用しない。Push専用の内部シークレットを使い、公開anon/publishable keyだけで配信関数を呼べる設計は禁止。
- 5分ごとに対象時刻を確認する案。30日なら8,640起動/月、31日なら8,928起動/月。2人×各2端末×朝夕×31日の最大通知数は248通/月（未完了なしは省略、再試行/テストを除く）。これは見積りで実測ではない。
- [Edge Functions公式料金](https://supabase.com/docs/guides/functions/pricing)ではFreeの呼出枠は500,000回。既存機能の呼出数/通信/DB容量と合算し確認する。無料枠内で運用できる見込みだが、利用量と可用性を保証しない。[Freeプロジェクトの休止条件](https://supabase.com/pricing)にも注意。Cronを休止回避の保証としない。
- 標準Web Push/VAPID方式を使い、Firebase SDKや新たな通知SaaSを必須にしない。[Chromeの標準方式](https://developer.chrome.com/blog/web-push-interop-wins)。配信先は各ブラウザーが払い出すApple/Google/Microsoft等のPushサービスとなる。暗号化した一般文と宛先情報を送るため、この外部経路も承認対象。
- VAPID秘密鍵・内部呼出シークレットはサーバーのSecrets/Vaultのみ。ブラウザーへ出すのはVAPID公開鍵。送信ライブラリのDeno互換性・最新仕様・ライセンス・エンドポイント制約は実装前に再検証する。

## データと権限の設計案

購読の保存先は非公開スキーマを第一候補とし、クライアントはメンバー認証済みの専用関数経由で操作する。購読URLは秘密の配送先として扱い、画面・ログ・PR・家計キャッシュへ載せない。

- 購読: 内部ID、user_id、端末表示名、endpointと暗号鍵、enabled、同意時刻、最終確認時刻、失効情報。endpointは一意、同じブラウザーで別アカウントに自動付け替えない。利用者ごとの登録数を制限する。
- 通知設定: 既存の朝夕時刻は維持。Pushの個人別許可と端末別許可を明示的に追加し、既存行はオフのまま移行する。
- 配信台帳: 購読ID/JST日付/朝夕の一意制約、予定時刻、状態、試行回数、次回試行時刻、エラー分類。本文・画像・秘密情報は記録しない。診断履歴は30日で削除する案。購読解除時は配送資格を即時に無効化し、その配送先/鍵を削除する。
- RLSとGRANTを別々に検証。配偶者でも他人の購読/鍵を取得・変更できない。匿名・非メンバーは不可。所有者は入力値でなく検証済みJWTから決め、user_metadataは使わない。履歴の配送状態をクライアントに書かせない。
- 登録/配信時ともメンバー資格を確認。サービス権限がRLSを迂回する点を明示し、関数内部でも本人/同意/有効状態を確認する。公開APIから任意宛先へ送信できないようにする。
- endpointはHTTPS・許可されたプロバイダーhost/pathのみ、userinfo/独自port/IP literal/localhost/プライベートIP/リダイレクトを拒否。実機で取得した正規パターンを確認し、未知hostを無条件に許可しない。サイズ/頻度上限、Origin/認証検証も必要。

## ログアウト・解除と安全なSW更新

- 解除時はサーバー無効化とブラウザーunsubscribeを行う。片方が失敗しても「停止完了」と表示せず、再試行できるようにする。
- ログアウト/アカウント切替では旧購読の停止を試み、ログアウト自体は妨げない。オフライン時のサーバー即時停止は保証できないので、端末側の購読解除とローカル同意状態の無効化を優先する。旧ユーザーの購読を新ユーザーへ引き継がない。
- 実装時に、解除直前にPushサービスが受け付けた配信の取消不能・失効検知遅延を実機で確認する。すでにキューにある一般文が遅れて届く可能性を隠さない。OSの通知許可拒否を回避せず、許可のない端末へ新規登録/配送しない。
- SWは既存登録scopeと更新確認を維持し、push/notificationclick処理を追加する。generateSWへのimportScriptsまたはinjectManifestの採否を検証で決定し、③のユーザー確認更新・別タブ入力保護・オフライン閲覧を回帰検証する。別scopeのSWを増殖させない。
- Push有効端末では既存useDailyReminderによるOS通知を止めて二重通知を避ける。画面内まとめは残す。Push未対応/未登録端末の現行動作は維持する。ブラウザーに端末識別情報や家計データを追加する場合はユーザー別/ログアウト消去の境界をテストする。

## 失敗と重複の扱い

- 複数の実行が重なっても、台帳の一意制約と原子的なジョブ確保（ロック/期限付きlease）で同じ配信を同時処理しない。
- 2xxは「Pushサービス受付」であり「本人が見た」とはしない。通信切断が受付後に起きるケースのexactly-onceは保証できない。一定の通知tag/topicと端末側重複判定で重複を減らす。
- 404/410は購読失効として停止し、本人の再登録を案内。429はRetry-Afterを尊重。5xx/ネットワーク失敗は5分・15分後など上限3試行、予定から1時間を超えたら終了。401/403は鍵/設定不備として自動連打しない。
- TTLは配信時点で残る有効期間までに限定（最大1時間）。DB障害/情報取得失敗は通知しない。失敗を家計操作の失敗に波及させない。
- [Web Pushプロトコルのステータス/TTL](https://web.dev/articles/push-notifications-web-push-protocol)。端末への不達にメールやSMSを自動追加しない。
