# 全機能 UI・レイアウト調査

調査日: 2026-09-21

## 調査範囲と確度

利用者のスマホスクリーンショット2枚、mainのa05e9a8、全機能の画面コンポーネント、App.css、LifePlanning.css、既存UI仕様を確認した。今回は調査のみ。アプリの実装、本番DB、本番配信は変更していない。

スクショ上の不具合とコード上の原因を確認した項目、コードから確認した構造上の問題、今後の実機検証が必要な改善案を分けて扱う。全画面の実機操作、文字拡大、ソフトキーボード、各OSの戻る操作は今回実施していない。過去のテスト成功は今回の全画面表示保証にはならない。

## 確認できた直接原因（最優先）

1. ホームの4機能が3列＋1個になる。
   - a05e9a8でApp.cssの `.function-chooser-grid` が2列から3列に変更された。
   - 900px以上では2列へ上書きされるため、狭い画面ほど3列になる逆転がある。
   - スクショの「ポイント」の途中改行、4枚目だけ下段、余白の偏りと一致する。
   - 対応: スマホは2×2を基本とし、文字拡大・極狭幅で必要なら1列。4機能の高さと余白をそろえる。
2. 暮らしの切替が2段になる。
   - LivingHubViewは3ボタンだが `.living-hub-tabs` は2列のまま。
   - 640px以下で各ボタン内がアイコン・名称・件数の3段、最低70pxになる。外側の2行化と合わさり高さが増える。
   - 対応: 買い物・在庫／家事／レシピを1行3枠にする。通常文字サイズでは1行を維持し、拡大時は文字を小さくせず横スクロールなどで対応。
3. 上記は機能数の限界ではなく、前回変更の対象セレクタの取り違えと切替の列数未更新が直接原因。

## 全体方針

- Warm Homeの配色と4機能を選ぶホームは維持する。
- スマホは「今いる機能」「主要操作」「一覧」が早く見える構成にする。
- 大分類は下部5項目、機能内の切替はコンパクトな1行。状態・担当などの絞り込みは切替と形を区別する。
- 3項目の切替は均等幅、数が増える場合は横スクロールを検討。選択中項目が隠れないようにする。
- 日常表示はコンパクトな行、詳細・編集は必要なときに開く。タップ領域は減らさない。
- PCでは横幅を一覧＋詳細に使い、スマホの縦長カードを単に引き延ばさない。

## 横断課題と再発防止

1. **CSSの追記・上書きが多い**: App.cssは約5,600行。旧暗色テーマ、明色テーマ、コントラスト修正、各機能の追加が同居し、旧蛍光色定義や!importantも残る。旧色が現在すべて見えているという意味ではない。共通トークン・レイアウト・機能別CSSに分け、競合する旧定義を整理する。
2. **見た目の共通化不足**: Header、機能切替、見出し＋追加、検索＋絞り込み、一覧行、空状態、編集面、確認操作を共通化する。セレクタを機能単位に限定し、他画面へ影響する変更を減らす。
3. **画面を戻ると状態がリセット**: Appの大分類は条件分岐で再マウントされ、各ビューはuseStateで初期タブに戻る。最後に見ていた小タブ・絞り込み・スクロール位置を保持する。履歴／URLとの連動は別途設計する。
4. **編集中の離脱**: 大分類移動で未保存入力が失われる可能性。フォームごとの下書きと離脱時の扱いを統一する。
5. **固定ナビとキーボード**: 下部ナビは維持しつつ、最終行・保存ボタン・トーストを覆わない余白を統一。iOS safe area、横向き、キーボード表示中の振る舞いは実機で確認する。現時点で全画面に重なりがあるとは断定しない。
6. **レスポンシブの基準が分散**: 370/420/560/600/640/760/900/1200/1400pxなどが混在。目的別に整理し、境界の直前直後も検証する。レシピは最大760pxのまま2列になり、家事・在庫はPC一覧2列の共通ルール対象外。横幅の使い方を機能ごとに決める。
7. **文字と操作サイズ**: 新規切替の件数10pxなど、既存仕様の補助文字13–14px目安から離れている。数値を小さくして詰めるより装飾を削る。小ボタン、disabledのopacity、長い日本語、200%文字拡大を確認する。
8. **アイコンの不統一**: SVGと文字記号（☐、◎、≡等）が混在。レシピの≡はメニューと誤認しやすいため、本・調理などの意味が分かるSVGへ。
9. **選択状態の意味付け**: 小タブによってaria-pressed／aria-selected／視覚クラスのみが混在。ボタングループか正式なタブかを決め、対応するパネル・フォーカス動作までそろえる。
10. **確認と結果通知**: window.confirmが複数画面で使われる。破壊操作の確認、完了操作、取り消し可能な操作を整理。完了のUndo追加は履歴・次回期限の整合性を伴うためCSS修正とは別実装にする。
11. **検証データ不足**: dev/life-planning.jsxには家事など空配列の画面があり、レシピ保存・削除・買い物連携が成功を返すだけの仮処理。これでは保存後の実表示や大量データ時の操作は検証できない。状態が変わる試験用データを用意する。
12. **描画品質の判定不足**: lint・ビルド・単体テストは列数の取り違えを検出していない。機能数、列数、ラベルの改行、一覧までの高さを検証項目に加える。

## 推奨する実装順

1. P0修正: ホーム2×2、暮らし1行3枠、既存画面への波及確認。
2. 共通UI整理: ヘッダー、見出し、小タブ、検索、フォーム表示、下部余白。まず買い物・在庫・家事に適用。
3. 各機能の情報整理: レシピの閲覧／編集、未来の多段フィルター、ポイントの今日優先、家計簿/OCR。
4. 操作状態保持・PC/iPad最適化・CSS整理と視覚回帰確認。

## 受け入れ確認案

- スマホ320/375/390/430px、タブレット768/820/1024px、PC1280/1440px、縦横両方向。ブレークポイント前後でもチェック。
- 4機能ホームは標準スマホで2×2。ポイントなどの名称が途中で分断されない。
- 暮らし3項目は標準スマホで1行。拡大表示でも切替項目へ到達できる。
- 390×844を基準に、買い物・家事の最初の一覧項目へ余計なスクロールなしで到達することを目標とする。実測前のため達成済みとはしない。
- 空／1件／30件以上／長い名前／エラー／オフライン／保存中で確認する。
- 全画面で一覧最終行と保存操作を下部ナビに隠さない。文字拡大時に切れない。図以外でページ全体の横スクロールが生じない。
- キーボード、フォーカス、選択状態、減らす動作設定、本文コントラストを確認する。
- 実装を変更した後に、スクショ比較と実操作で検証する。テスト件数だけを表示保証に使わない。
